# 日常开发工作流（中文）

把 AI 当作**没有记忆、一开工就写代码**的协作工程师：用固定流程约束它，质量会稳定很多。

本 skill 将 [AI Hero 推荐的 5 个日常 skill](https://www.aihero.dev/5-agent-skills-i-use-every-day) 整合为一条流水线。每个阶段可单独使用，也可从头到尾走一遍。

```
想法/需求 → ① 拷问设计 → ② 写 PRD → ③ 拆 Issue → ④ TDD 实现 → ⑤ 架构加深（周期性）
```

---

## 何时用哪个阶段

| 用户意图 | 进入阶段 |
|----------|----------|
| 「帮我想清楚」「拷问一下方案」「grill me」 | **① 拷问设计** |
| 「写成 PRD / 需求文档」「整理成规格」 | **② 写 PRD**（通常需先完成 ①） |
| 「拆成任务 / issue」「怎么分步做」 | **③ 拆 Issue** |
| 「用 TDD 做」「先写测试」「红绿重构」 | **④ TDD 实现** |
| 「架构体检」「模块太深/太浅」「方便 AI 改代码」 | **⑤ 架构加深** |

若用户只说「做一个 X 功能」，默认顺序：**① → ② → ③ → ④**；⑤ 建议在功能合并后或每周固定做一次。

---

## ① 拷问设计（grill-me）

**目标**：在写任何 PRD 或代码之前，与用户对齐「设计树」上的每一个分叉（参考 Brooks《The Design of Design》）。

**核心指令**（对用户当前方案执行）：

> 就这个方案的每个方面持续追问，直到我们达成共同理解。沿设计树的每条分支往下走，**一次只解决一个决策及其依赖**。每个问题给出你的**推荐答案**供参考。  
> **一次只问一个问题。**  
> 若问题可以通过阅读代码库回答，**先去读代码库**，不要空问。

**规则**：

- 不要过早输出完整「计划文档」；对话优先于文档。
- 复杂功能可能需 20～50 轮问答，属正常现象。
- 探索代码库时：读相关模块、现有 API、测试与 ADR（若有）。

**结束条件**：用户明确表示「可以写 PRD 了」或「开始拆任务」。

---

## ② 写 PRD（to-prd）

**目标**：把当前对话与代码库理解沉淀为**产品需求文档**，供人与 Agent 共同执行。

**前置**：理想情况下已完成 ①；若对话已充分对齐，可跳过再次访谈，直接综合。

**流程**：

1. **探索仓库**（若尚未做过）：现状、领域术语、相关 ADR、可复用模块。
2. **勾勒主要模块**：列出需要新建或修改的模块；主动寻找可**单独测试的深模块**（接口小、行为多、变更少）。
3. **与用户确认**：模块划分是否符合预期；哪些模块需要测试覆盖。
4. **按模板撰写 PRD**（见下方），发布到用户指定的载体：
   - GitHub Issue / 项目 Issue _tracker
   - 或 `docs/prd/<功能名>.md`（用户未指定时询问偏好）

**PRD 模板**：

```markdown
## 问题陈述
从用户视角描述要解决的问题。

## 解决方案
从用户视角描述期望的解决方式。

## 用户故事
编号列表，格式：
1. 作为<角色>，我希望<能力>，以便<价值>

应尽可能覆盖该功能的全部行为面。

## 实现决策
- 将新建/修改的模块及职责
- 模块对外接口（类型、不变量、错误模式、顺序约束）
- 架构决策、 schema / API 契约、关键交互
- 技术澄清（来自开发者）

不要写具体文件路径或易过时的代码片段。
例外：若原型中的片段（状态机、 reducer、 schema）比文字更精确，可精简摘录并注明来自原型。

## 测试决策
- 何谓「好测试」（测对外行为，不测实现细节）
- 哪些模块要测
- 仓库中的测试先例（类似测法）

## 不在范围内
明确排除项。

## 其他说明
```

**发布**：若使用 Issue，加上项目约定的「可交给 Agent」类标签（如 `ready-for-agent`）；标签名以仓库惯例为准。

## ③ 拆 Issue（to-issues）

**目标**：把 PRD（或计划）变成**可独立领取**的工作项，每项是**纵向切片（tracer bullet）**，而非「先做完所有后端再做前端」的横向分层。

**流程**：

### 1. 收集上下文
- 使用对话中已有 PRD；若用户给出 Issue 编号/URL/路径，读取全文与评论。

### 2. 探索代码库（可选）
- 若尚未探索，先了解现状，Issue 标题与描述使用项目**领域词汇**。

### 3. 起草纵向切片
每条切片：
- 贯穿**所有集成层**（如：schema → API → UI → 测试）的**窄而完整**路径
- 完成后可**演示或验证**
- 切片宜**细**不宜粗

**类型**：
- **AFK**：Agent 可独立完成并合并，优先采用。
- **HITL**：需人决策（架构选型、设计评审等）。

### 4. 与用户确认
以编号列表展示，每项包含：

| 字段 | 说明 |
|------|------|
| 标题 | 简短描述 |
| 类型 | HITL / AFK |
| 阻塞于 | 须先完成的其他切片编号，或「无」 |
| 覆盖的用户故事 | 对应 PRD 中的编号 |

询问：粒度是否合适？依赖是否正确？是否合并/再拆？HITL/AFK 标记是否准确？  
**迭代直到用户批准。**

### 5. 发布 Issue
按**依赖顺序**创建（先创建被依赖项，以便在「阻塞于」中引用真实编号）。

**Issue 正文模板**：

```markdown
## 父级
（若来自已有 Epic/PRD Issue，填链接；否则省略）

## 要做什么
描述本切片的端到端行为，不要按「层」罗列实现步骤。
避免易过时的文件路径；原型片段规则同 PRD。

## 验收标准
- [ ] 可验证条件 1
- [ ] 可验证条件 2

## 阻塞于
- #123（或写「无，可立即开始」）
```

不要关闭或修改父级 PRD Issue。

## ④ TDD 实现（tdd）

**目标**：用**红 → 绿 → 重构**循环提高实现质量；**禁止**「先写完全部测试再写完全部代码」的横向切片。

### 哲学（必须遵守）

- 测试通过**公共接口**验证**行为**，不绑实现细节。
- **好测试**：像规格说明书——「用户可用有效购物车结账」；重构内部实现时仍应通过。
- **坏测试**： mock 内部协作方、测私有方法、绕过接口直查 DB；重构未改行为却失败。

### 工作流

#### 1. 规划（写任何产品代码前）
- [ ] 与用户确认需要变化的**公共接口**
- [ ] 确认优先测哪些**行为**（不能全测，聚焦关键路径与复杂逻辑）
- [ ] 识别**深模块**机会（小接口、厚实现）
- [ ] 列出待测行为清单，获用户认可

问用户：「对外接口应长什么样？哪些行为最值得测？」

#### 2. 首发 tracer bullet
```
红：写一条测试，验证一个行为 → 失败
绿：写最少代码通过 → 通过
```

#### 3. 增量循环（每个行为重复）
```
红：下一条测试 → 失败
绿：最少实现 → 通过
```
规则：**一次一条测试**；不写投机功能；不预判后续测试。

#### 4. 重构（全部变绿后）
- 去重、加深模块、自然运用 SOLID
- **禁止在仍处「红」时重构**
- 每步重构后跑测试

### 每轮自检
- [ ] 测试描述的是行为而非实现
- [ ] 只使用公共接口
- [ ] 内部重构不应导致测试失败
- [ ] 代码仅为当前测试服务
- [ ] 无投机功能

## ⑤ 架构加深（improve-codebase-architecture）

**目标**：发现**浅模块**与接缝混乱，提出**加深**机会，提升可测性与 AI 可导航性。建议**每周一次**或在一波密集开发之后执行。

### 术语（报告中统一使用）

| 术语 | 含义 |
|------|------|
| **模块** | 有接口与实现的单元（函数、类、包、切片） |
| **接口** | 调用方需知道的一切：类型、不变量、错误、顺序、配置 |
| **实现** | 模块内部代码 |
| **深度** | 接口背后行为/复杂度的比值；**深** = 小接口大能力 |
| **接缝** | 可替换行为而不改调用方的地方 |
| **适配器** | 接缝上的具体实现 |
| **删除测试** | 若删掉模块后复杂度消失 → 可能是透传；若复杂度散落到 N 个调用方 → 模块有价值 |

**接口即测试面。**

### 流程

#### 1. 探索
先读项目领域词汇表（如 `CONTEXT.md`）及相关 ADR。

探索时记录摩擦：
- 理解一个概念是否要跳很多小文件？
- 接口是否几乎和实现一样复杂（浅）？
- 是否为可测性拆了纯函数，但真正 bug 在调用方式（无**局部性**）？
- 紧耦合是否泄漏过接缝？
- 哪些区域难测或缺乏测试？

对可疑浅模块做**删除测试**。

#### 2. 输出报告
将自包含 HTML 写到系统临时目录（`$TMPDIR` 或 `/tmp`），文件名含时间戳，**不要提交进仓库**。  
用 Tailwind CDN + Mermaid CDN；每项候选一张卡片，含：

- **涉及文件/模块**
- **问题**
- **方案**（ plain 中文）
- **收益**（局部性、杠杆、测试如何改善）
- **前后对比图**
- **推荐强度**：`强烈` / `值得探索` / `推测性`

文末：**首选建议**及理由。

用 `CONTEXT.md` 中的领域词命名模块；若与 ADR 冲突，仅在摩擦足够大时标注并说明是否值得重开 ADR。

**此阶段只呈现候选，不直接改代码。** 询问用户：「想深入哪一项？」

#### 3. 拷问循环（用户选定后）
回到 **① 拷问设计**：约束、依赖、加深后的模块形状、接缝背后放什么、哪些测试应长期存在。

边讨论边更新（若项目有）：
- `CONTEXT.md` 新术语
- 用户拒绝某重构且理由持久 → 可提议写 ADR 避免重复建议

## 端到端示例

**场景**：为后台增加「导出 CSV」

1. **①** 一次一问：谁导出？权限？大数据量分页还是异步任务？失败如何提示？… 必要时读现有导出/权限代码。
2. **②** 输出 PRD：用户故事 + 模块（ExportService 深模块）+ 测试决策。
3. **③** 切片示例：
   - #1 AFK：最小路径「单页表格 CSV 下载」含 API + 测试
   - #2 AFK：大结果集异步 + 轮询状态
   - #3 HITL：权限模型与产品确认
4. **④** 对 #1 做 TDD：先测「认证用户请求合法表 ID 得到 CSV 响应头与内容」→ 实现 → 重构。
5. **⑤** 一周后：发现 Export 与 Permission 在 6 个文件间跳转 → 报告建议加深 Export 模块接口。

## Agent 行为总则

1. **先流程后代码**：未对齐设计树前，不大量写实现。
2. **能读库就不猜**：仓库能回答的问题，用工具探索。
3. **纵向优于横向**：拆任务与 TDD 都优先 end-to-end 细切片。
4. **文档与 Issue 用领域语言**：与代码库、产品用语一致。
5. **尊重已有 ADR**：架构建议不与既定决策冲突，除非明确标注需重议。
6. **阶段可跳过但需说明**：例如用户只要 TDD，则跳过 ①②③，但仍要做 TDD 的规划步骤。
