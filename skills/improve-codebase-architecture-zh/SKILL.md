# 改进代码库架构（improve-codebase-architecture）

发现架构摩擦，提出**加深机会**——把**浅模块**变成**深模块**。目标是可测性与 AI 可导航性。

## 术语

全文统一使用下列术语（不要用「组件」「服务」「边界」等替代「模块」「接缝」）：

| 术语 | 含义 |
|------|------|
| **模块** | 有接口与实现的单元（函数、类、包、切片） |
| **接口** | 调用方需知道的一切：类型、不变量、错误模式、顺序、配置——不仅是类型签名 |
| **实现** | 模块内部代码 |
| **深度** | 接口处的杠杆：接口小、背后行为多。**深** = 高杠杆；**浅** = 接口几乎和实现一样复杂 |
| **接缝** | 接口所在之处；可在不就地修改的情况下改变行为的地方 |
| **适配器** | 在接缝上满足接口的具体实现 |
| **杠杆** | 调用方从深度中获得的能力 |
| **局部性** | 维护方从深度中获得的能力：变更、缺陷、知识集中在一处 |

关键原则：

- **删除测试**：想象删掉该模块。若复杂度消失 → 可能是透传；若复杂度散落到 N 个调用方 → 模块在发挥作用。
- **接口即测试面。**
- **一个适配器** = 假想的接缝；**两个适配器** = 真实的接缝。

本 skill 应结合项目的领域模型：领域语言为好的接缝命名；**ADR** 记录已做决策，不应轻易重议。

## 流程

### 1. 探索

先读项目领域词汇表（如 `CONTEXT.md`）及将要改动区域的 **ADR**。

然后有机地浏览代码库，记录摩擦：

- 理解一个概念是否要在许多小模块间跳转？
- 哪些模块**浅**——接口几乎和实现一样复杂？
- 是否为可测性拆了纯函数，但真正 bug 在调用方式（缺乏**局部性**）？
- 紧耦合模块是否泄漏过**接缝**？
- 哪些部分未测或难以通过当前**接口**测试？

对可疑浅模块做**删除测试**。

### 2. 以 HTML 报告呈现候选

将**自包含 HTML** 写到系统临时目录（`$TMPDIR`，否则 `/tmp`；Windows 用 `%TEMP%`），文件名如 `architecture-review-<时间戳>.html`，**不要提交进仓库**。

为用户打开报告（Linux：`xdg-open`；macOS：`open`；Windows：`start`），并告知绝对路径。

报告可用 Tailwind CDN 排版、Mermaid CDN 画关系图；需要时用自定义 CSS/SVG。每个候选一张卡片，包含：

- **文件**：涉及的文件/模块
- **问题**：当前架构为何造成摩擦
- **方案**：用 plain 中文描述将发生什么变化
- **收益**：从局部性、杠杆、测试改善角度说明
- **前后对比图**：并排展示浅与加深后的结构
- **推荐强度**：`强烈` / `值得探索` / `推测性`（徽章展示）

文末：**首选建议**——先做哪一项及原因。

用 `CONTEXT.md` 中的领域词描述模块（例如「订单 intake 模块」，而非 `FooBarHandler`）。

**与 ADR 冲突**：仅当摩擦足够大、值得重议 ADR 时才提出；在卡片中明确标注（例如：「与 ADR-0007 冲突，但值得重开，因为……」）。不要罗列 ADR 已禁止的所有理论重构。

**此阶段不要提出具体接口设计。** 报告完成后问用户：「你想深入哪一项？」

### 3. 拷问循环

用户选定候选后，进入 **`grill-me-zh`** 式对话：沿设计树讨论约束、依赖、加深后的模块形状、接缝背后放什么、哪些测试应长期存在。

讨论中可产生的副作用：

- 加深后的模块命名使用了 `CONTEXT.md` 中没有的概念 → 更新 `CONTEXT.md`（无则懒创建）
- 对话中澄清了模糊术语 → 当场更新 `CONTEXT.md`
- 用户拒绝候选且理由持久 → 可提议写 **ADR**，避免日后架构审查重复建议（跳过「现在不值得」等短暂理由）
- 需探索加深模块的多种接口形状 → 与用户逐项对比利弊

## 节奏

建议**每周一次**，或在一波密集开发之后做一次。代码库越清晰，Agent 产出质量越高。
