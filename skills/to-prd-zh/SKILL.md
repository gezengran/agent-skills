# 写 PRD（to-prd）

根据**当前对话上下文**与对代码库的理解，产出一份 PRD。

**不要访谈用户**——综合你们已经对齐的内容即可。若信息明显不足，可请用户补充**一段**说明，而不是重新做完整拷问（拷问请用 `grill-me-zh`）。

## 流程

### 1. 探索仓库

若尚未探索：了解现状；全文使用项目的**领域词汇**；遵守相关 **ADR**。

### 2. 勾勒主要模块

列出需要新建或修改的模块。主动寻找可**单独测试的深模块**：

**深模块**（相对浅模块）：在**简单、稳定、可测的接口**背后封装大量行为。

与用户确认：

- 模块划分是否符合预期
- 哪些模块需要编写测试

### 3. 撰写并发布 PRD

使用下方模板。发布位置由用户指定，未指定时询问：

- 项目 Issue 跟踪器（如 GitHub Issue）
- 或 `docs/prd/<功能名>.md`

若使用 Issue，可加上项目约定的「可交给 Agent」类标签（如 `ready-for-agent`）。

## PRD 模板

```markdown
## 问题陈述

从用户视角描述要解决的问题。

## 解决方案

从用户视角描述解决方案。

## 用户故事

编号列表，每条格式：

1. 作为<角色>，我希望<能力>，以便<价值>

示例：
1. 作为手机银行用户，我希望查看各账户余额，以便更好地控制支出。

列表应尽可能完整，覆盖该功能的全部行为面。

## 实现决策

可包括：

- 将新建/修改的模块
- 这些模块将被修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**写具体文件路径或代码片段（极易过时）。

**例外**：若原型中的片段（状态机、reducer、schema、类型形状）比 prose 更精确，可在对应决策下精简摘录，并注明来自原型——只保留决策相关部分，不是可运行 demo。

## 测试决策

- 何谓本项目的「好测试」（通常：只测对外行为，不测实现细节）
- 哪些模块要测
- 仓库中的测试先例（类似测法）

## 不在范围内

明确排除项。

## 其他说明

任何补充说明。
```
