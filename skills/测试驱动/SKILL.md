# 测试驱动开发（TDD）

## 哲学

**核心原则**：通过**公共接口**验证**行为**，不绑实现细节。实现可以大改，测试不应无谓失败。

**好测试**是集成风格：走真实代码路径、调用公共 API。描述系统**做什么**，不是**怎么做**。例如「用户可用有效购物车结账」——读测试即读规格；重构内部结构时仍应通过。

**坏测试**绑在实现上： mock 内部协作者、测私有方法、绕过接口直查数据库等。警告信号：行为未变但测试因重构失败；或重命名内部函数导致测试挂掉——说明测的是实现，不是行为。

## 反模式：横向切片

**禁止**先写完全部测试再写完全部实现。那是把 RED 当成「写所有测试」、GREEN 当成「写所有代码」。

后果：

- 批量写的测试针对**想象**的行为，不是**真实**行为
- 容易测「形状」（数据结构、签名）而非用户可见行为
- 测试对真实变更不敏感
- 在尚未理解实现前就定下测试结构

**正确做法**：纵向 tracer bullet——**一条测试 → 一点实现 → 重复**。

```
错误（横向）：
  红：  test1, test2, test3, test4, test5
  绿：  impl1, impl2, impl3, impl4, impl5

正确（纵向）：
  红→绿： test1 → impl1
  红→绿： test2 → impl2
  ...
```

## 工作流

### 1. 规划

探索代码库时使用项目**领域词汇**；遵守相关 **ADR**。

写任何产品代码前：

- [ ] 与用户确认需要哪些**接口变更**
- [ ] 与用户确认优先测哪些**行为**（不能全测）
- [ ] 识别**深模块**机会（小接口、厚实现）
- [ ] 为**可测性**设计接口
- [ ] 列出待测行为（不是实现步骤清单）
- [ ] 获得用户对计划的认可

问用户：「公共接口应长什么样？哪些行为最值得测？」

**测不完一切。** 与用户确认最关键的行为，聚焦关键路径与复杂逻辑，而非每个边角。

### 2. Tracer bullet

写**一条**测试，验证**一件事**：

```
红：  写第一条行为的测试 → 失败
绿：  写最少代码通过 → 通过
```

这是贯穿端到端的首发 tracer bullet。

### 3. 增量循环

对其余每个行为重复：

```
红：  写下一条测试 → 失败
绿：  最少实现 → 通过
```

规则：

- **一次一条测试**
- 只为通过**当前**测试写代码
- 不要预判后续测试
- 测试聚焦可观察行为

### 4. 重构

全部变绿后，寻找重构机会：

- [ ] 消除重复
- [ ] 加深模块（把复杂度藏到简单接口后）
- [ ] 在自然处应用 SOLID
- [ ] 思考新代码对既有代码的启示
- [ ] 每步重构后跑测试

**禁止在仍为「红」时重构。** 先变绿。

## 每轮自检

```
[ ] 测试描述的是行为，不是实现
[ ] 测试只使用公共接口
[ ] 内部重构不应导致测试失败
[ ] 代码仅为当前测试服务
[ ] 未添加投机功能
```
